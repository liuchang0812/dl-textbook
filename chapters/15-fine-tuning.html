微调与 LoRA

你几乎永远不需要从零训练一个大模型，但你很可能需要一个懂你业务的模型。 这一章讲微调——以及一个让这件事变得人人都能做的技巧： LoRA 只训练原模型 0.1% 的参数， 让你用一张消费级显卡就能改造一个 33B 的模型。

15.1 先问：真的需要微调吗？

这是最重要的一节。很多人在应该用提示工程或 RAG 的时候选择了微调， 浪费了几周时间和几千美元，最后效果还不如原来。

你的需求该用什么为什么
让模型知道你的公司文档内容 RAG（第 17 章） 知识是会变的。微调进权重的知识无法更新，也无法引用出处。 而且模型会「记混」，把相似的事实混在一起。
让模型按特定格式输出 JSON 提示工程 + 结构化输出 现代模型的指令遵循能力很强，一个好的提示 + 几个示例通常就够了。
让模型学会一种新的行为方式
（语气、推理风格、领域术语）		 微调 ✅ 这属于「风格」而不是「知识」。风格很难用提示描述清楚， 但用几百个例子就能教会。
降低推理成本 / 延迟 微调小模型 ✅ 用一个 7B 的微调模型替代调用 GPT-4，成本能降两个数量级。
需要私有部署（数据不能出内网） 微调 + 本地部署 ✅ 开源模型 + 微调是唯一的方案。
需要某个特定任务的极致准确率 微调 ✅ 任务越窄、数据越专，微调的优势越大。
一条简单的判断规则

知识 → RAG。行为 → 微调。

想改变模型「知道什么」，用检索；想改变模型「怎么做」，用微调。 两者不冲突，实践中经常结合使用：先 RAG 提供事实， 再用微调过的模型以你想要的风格和格式输出。

15.2 全参数微调有多贵

「微调」最朴素的理解是把预训练模型拿来，用你的数据继续训练所有参数。 这叫全参数微调（Full Fine-Tuning），它的成本和预训练是同量级的。

回顾第 12 章讲的显存构成。一个 7B 模型全参数微调需要：

项目精度显存
模型权重bf1614 GB
梯度bf1614 GB
Adam 一阶矩 + 二阶矩fp3256 GB
fp32 主权重fp3228 GB
激活值（取决于批量与序列长度）—10~30 GB
合计约 120~140 GB

也就是说，微调一个 7B 模型至少要两张 A100 80G，或者用 ZeRO-3 分片到 8 张卡上。 而如果你要微调 70B，那需要几十张卡——对个人和小团队来说完全不可行。

还有一个容易被忽略的问题：灾难性遗忘。 全参数微调会让模型在你的小数据集上「跑偏」， 原有的通用能力（对话、推理、写代码）会明显退化。

15.3 LoRA：一个漂亮的数学技巧

2021 年，微软的研究者提出了 LoRA（Low-Rank Adaptation）。 它的核心假设是：

LoRA 的核心假设

微调时权重的变化量 $\Delta W$ 是低秩的。

也就是说：从通用模型变成你的专用模型，不需要改动 70 亿个参数的方向， 只需要在一个很小的子空间里调整就够了。

基于这个假设，LoRA 的做法是：

$$h = W_0 x + \Delta W x = W_0 x + \underbrace{B A}_{\text{低秩分解}} x$$
$W_0$ 是冻结的原始权重（$d \times k$）， $B$ 是 $d \times r$，$A$ 是 $r \times k$，且 $r \ll \min(d,k)$
LoRA 的结构。原始权重 $W_0$ 完全冻结， 旁边挂两个小矩阵 $A$ 和 $B$。训练时只更新 $A$ 和 $B$， 前向传播时把两个分支的输出相加。
◈为什么要「零初始化 B」？

如果 $A$ 和 $B$ 都是随机的，那么训练刚开始时 $\Delta W = BA$ 就是一个随机矩阵——模型的行为会立刻被破坏。

把 $B$ 初始化为全 0，$\Delta W = 0$，模型在训练开始时和原模型完全一致。 然后随着训练，$\Delta W$ 逐渐从 0 长出来。 这是一个「平滑起步」的设计，让训练一开始就站在一个很好的点上。

前向传播时的细节

LoRA 论文里还有一个容易被忽略的缩放因子：

$$h = W_0 x + \frac{\alpha}{r} B A x$$
$\alpha$ 是一个常数（通常设为 $2r$），$\alpha/r$ 用来保持不同 $r$ 下的更新幅度一致

为什么要这个缩放？因为当 $r$ 变化时，$BA$ 的数值尺度也会变。 如果不缩放，你换了 $r$ 之后就得重新调学习率。 有了 $\alpha/r$，你就可以固定 $\alpha$、自由地调整 $r$， 而不用重调其他超参数。

15.5 QLoRA：把基座模型也量化

LoRA 省了优化器状态的显存，但基座模型本身还是 fp16， 7B 模型仍要 14 GB。对只有一张 24GB 显卡的人来说还是紧张。

2023 年的 QLoRA 进一步解决了这个问题：把冻结的基座模型量化成 4-bit。

方案7B 模型显存33B 模型显存65B 模型显存
全参数微调约 120 GB约 550 GB约 1100 GB
LoRA（bf16 基座）约 22 GB约 90 GB约 175 GB
QLoRA（4-bit 基座）约 8 GB约 24 GB约 48 GB

看最后一行：QLoRA 让一张 24GB 的消费级显卡（比如 RTX 4090）能微调 33B 的模型。 这直接把微调从「需要数据中心」变成了「一台游戏电脑就能做」。

QLoRA 的三个关键技术

  1. NF4 量化。不是普通的均匀量化，而是假设权重服从正态分布， 在分布密集的区域用更细的量化级别。信息论上这是对正态分布最优的 4-bit 表示。
  2. 双重量化。量化本身需要存储缩放系数（每个 64 个权重一个 fp32）。 双重量化把这些缩放系数再量化一次，每个参数平均再省 0.37 bit。 听起来很少，但对 65B 模型就是 3 GB。
  3. 分页优化器。用 NVIDIA 的统一内存，在显存峰值时自动把优化器状态 换出到内存。避免因为一个瞬时峰值而 OOM。
⚠QLoRA 的代价

4-bit 基座 + bf16 LoRA 的混合精度计算，速度比纯 bf16 LoRA 慢约 20%~40%， 因为每次前向都要把 4-bit 权重反量化。

所以取舍是：显存换时间。如果你有足够的显存，用 bf16 LoRA 更快； 如果显存是瓶颈，QLoRA 让你能做这件事（而不是做不了）。

✓「一个基座 + 多个适配器」的价值

每个 LoRA 适配器只有几十 MB，而基座模型是 14 GB。 这意味着你可以用一份基座，挂上几十个不同任务的适配器， 在推理时动态切换。

这对多租户的 SaaS 服务非常有价值： 每个客户有自己专属的适配器，但共享同一份基座权重， 显存占用几乎不增加。这是 LoRA 相比全参数微调最实用的优势之一。

15.7 超参数怎么选

参数推荐值说明
秩 r 8 ~ 64 任务越复杂、数据越多，r 越大。简单风格调整 r=8 够，学新能力用 32~64。 超过 128 通常没有额外收益。
lora_alpha 2r 固定用 2r 是社区惯例，能让你自由调 r 而不用重调学习率。
learning rate 1e-4 ~ 3e-4 比全参数微调大 10~100 倍。因为只训练少量参数， 需要更大的步长才能有效更新。这是新手最容易设错的地方。
target_modules q,k,v,o + FFN 全部 只调 q、v 是原始论文的省钱配置；加上 FFN 效果更好， 因为 FFN 存了大部分事实知识。
epochs 2 ~ 5 LoRA 很容易过拟合。超过 5 轮通常开始退化， 尤其是数据量小的时候。
数据量 500 ~ 10000 条 质量比数量重要。500 条精挑的数据能显著改变模型风格； 想学新知识则需要更多。
lora_dropout 0.05 ~ 0.1 数据量少时调高一点防止过拟合。
⚠三个最常见的翻车原因

1. 学习率设成 2e-5。这是全参数微调的学习率。 LoRA 只训练少量参数，用这么小的学习率几乎学不动。 看到「loss 一直在 2.3 附近不动」时，第一反应应该是「学习率太小了」。

2. 训练和推理的对话模板不一致。 训练时用了 apply_chat_template， 推理时手写 prompt 格式不同，模型就完全不知道该干什么。 一定要用同一套模板。

3. 对指令部分也计算损失。 这会让模型学会「生成问题」而不是「回答问题」。 表现为：你问它问题，它给你生成更多问题。

15.8 其他 PEFT 方法

LoRA 不是唯一的参数高效微调方法。了解它们的思路有助于选择合适的工具：

方法核心思路可训练参数特点
Adapter 在层之间插入小的瓶颈网络 3~5% 最早的方法，会增加推理延迟（因为层变多了）
Prefix Tuning 在每层前面拼接一段可学习的「虚拟 token」 0.1~1% 参数极少，但占用上下文长度，训练不稳定
Prompt Tuning 只在输入层加一段可学习的 soft prompt 0.01% 参数最少，但效果随模型变小而急剧下降
LoRA 低秩分解权重增量 0.1~1% 可以合并回原权重，推理零开销。当前的主流
IA³ 用向量缩放激活值 0.01% 参数极少，效果接近 LoRA
DoRA 把权重分解成「方向」和「大小」，分别微调 略多于 LoRA 效果通常略优于 LoRA，但更慢
LoRA 最大的工程优势

它是上表里唯一一个「推理时零额外开销」的方法。

因为 $W_{\text{new}} = W_0 + BA$ 可以直接算出来并合并回原权重。 合并后模型就是一个普通的 Transformer，没有任何额外的层或计算。

Adapter 和 Prefix Tuning 都会在推理时引入额外的计算或上下文占用。 在要求低延迟的生产环境里，这一点往往比「效果好 0.5 个点」更重要。

15.9 本章小结

全参数微调 FFT
更新模型所有参数。显存需求高（7B 要 120GB），容易灾难性遗忘。
LoRA
冻结原权重，只训练两个低秩矩阵 $A$、$B$。可训练参数降至 0.1%~1%。
秩 rank, r
低秩矩阵的中间维度。越大容量越强，但参数也越多。通常 8~64。
QLoRA
把冻结的基座量化成 4-bit，让消费级显卡能微调 33B 模型。
PEFT
参数高效微调的总称。LoRA、Adapter、Prefix Tuning 等都属于这一类。
灾难性遗忘
在新任务上训练导致原有能力退化。LoRA 因为冻结基座，天然缓解这个问题。
  1. 先判断需求：知识用 RAG，行为用微调。大部分场景不需要微调。
  2. 全参数微调的显存需求是预训练级别的，7B 就要 120 GB。
  3. LoRA 的核心假设是「权重变化量是低秩的」，用 $BA$ 近似 $\Delta W$。
  4. $B$ 零初始化让训练从「和原模型完全一致」开始，是 LoRA 稳定性的关键。
  5. QLoRA 把基座量化到 4-bit，让 24GB 显卡能微调 33B 模型，代价是慢 20~40%。
  6. LoRA 学习率要比全参数微调大 10~100 倍（1e-4 量级），这是最常见的错误。
自测 · 点开看答案
公司想让你做一个「懂内部文档的问答助手」，你会选 RAG 还是微调？

RAG，而且几乎没有犹豫的余地。四个理由：

① 文档会变。公司制度、产品文档每周都在更新。 微调进权重的知识是「冻结」的，要更新就得重新训练。 RAG 只要更新向量库，几分钟就能生效。

② 需要引用出处。内部问答场景下，用户需要知道答案来自哪个文档。 微调模型无法给出出处，而 RAG 天然可以。

③ 模型会记混。微调把知识压进参数里， 相似的条款容易被混淆（「年假 15 天」和「病假 15 天」可能串了）。 RAG 是精确检索，不会混。

④ 成本更低、迭代更快。RAG 不需要 GPU 训练，调试周期是天级而不是周级。

微调在这里唯一可能的用处是：让模型学会以公司期望的口吻和格式 回答（比如必须分点、必须给出处链接）。这是「行为」，不是「知识」。

为什么 LoRA 的 B 矩阵要初始化为 0？

为了让训练从一个「模型行为完全不变」的起点开始。

如果 $A$ 和 $B$ 都随机初始化，那么 $\Delta W = BA$ 就是一个随机矩阵。 前向传播时 $h = W_0x + BAx$，第二项是一个随机扰动—— 相当于你在一个训练好的模型上加了一堆噪声，模型能力立刻被破坏。 训练初期需要先「修复」这个破坏，浪费了大量步数。

把 $B$ 初始化为 0 后，$\Delta W = 0$，模型行为和原模型完全一致。 然后随着训练，$\Delta W$ 从 0 平滑地长出来。

这也解释了为什么 LoRA 通常不需要 warmup—— 它的起点本来就是一个很好的点，不像随机初始化的模型需要小心起步。

LoRA 微调时，学习率应该设成多少？为什么？

1e-4 到 3e-4，也就是比全参数微调（通常 1e-5 ~ 2e-5）大 10~100 倍。

原因：全参数微调时，每个参数都在被更新，整体的更新量累积起来很大。 而 LoRA 只训练 0.1%~1% 的参数，如果还用那么小的学习率， 这些参数几乎不会移动，模型也就学不到东西。

实际表现就是：loss 一直卡在 2.3（随机猜测的水平）附近不动。 这时候第一反应应该是「学习率是不是太小了」，而不是怀疑数据或代码。

另外注意 LoRA 的学习率上限通常比全参数微调更敏感—— 设成 1e-3 以上容易训练不稳定。所以 1e-4 ~ 3e-4 是比较安全的区间。

QLoRA 用了 4-bit 量化，为什么还能训出 bf16 精度的 LoRA 适配器？

因为量化的只是「冻结的基座」，LoRA 适配器本身始终是 bf16 的。

前向传播时的流程是： ① 从 4-bit 存储的 $W_0$ 反量化成 bf16； ② 用 bf16 计算 $W_0x$ 和 $BAx$，两者相加得到输出。

所以只有 $W_0$ 的存储是 4-bit 的， 计算过程全程是 bf16。这带来的精度损失很小——因为 $W_0$ 是冻结的，它只需要「大致正确」就够了， 真正需要精细调整的部分（$\Delta W$）保留了完整精度。

这也是 QLoRA 论文的核心发现： 量化冻结的权重对最终效果影响很小，而量化被训练的权重才是灾难。

为什么说「一个基座 + 多个 LoRA 适配器」很有价值？

因为适配器的体积只有基座模型的千分之几。

一个 7B 模型是 14 GB，而一个 LoRA 适配器（r=16，全模块）通常只有 50~200 MB。 这意味着你可以用一份基座权重，挂上几十上百个不同任务的适配器。

实际价值体现在几个方面：

① 多租户 SaaS：每个客户有自己的适配器，但共享同一份基座， 显存占用几乎不增加，还能按需动态切换。

② 版本管理与 A/B 测试：适配器体积小，易于存储、分发和回滚。 可以同时部署多个版本做对比实验。

③ 快速迭代：发现某个任务效果不好，重新训一个适配器只要几小时， 不需要重新部署整个模型。

这是 LoRA 相比全参数微调在工程上最实用的优势—— 它把「模型」变成了「基座 + 可插拔的插件」。
