第 14 章 · 第五部 大模型工程

推理与部署

训练是几千万美元的一次性投入，推理是每天都在烧的钱。 一个 70B 模型光权重就要 140 GB，生成 1000 个 token 要跑 1000 次前向传播。 这一章讲怎么让它跑得动、跑得快、跑得便宜： KV Cache、量化、采样策略、连续批处理。

14.1 推理的两个阶段

LLM 的推理和训练有一个根本区别：它是逐 token 生成的。 要生成 500 个 token，就要跑 500 次前向传播。

而这 500 次里，第一次和后面 499 次的性质完全不同：

两个阶段的本质差异。Prefill 是「算力密集」， Decode 是「显存带宽密集」。这两种瓶颈需要完全不同的优化手段。
为什么 Decode 是带宽瓶颈？

生成一个 token，需要把全部模型权重读一遍。 一个 70B 的 bf16 模型是 140 GB，H100 的显存带宽约 3.35 TB/s， 所以读一遍至少要 $140/3350 \approx 42$ 毫秒。

而这一遍读取只做了约 $2 \times 70\text{B} = 1.4\times10^{11}$ FLOPs 的计算， 相当于 H100 峰值算力的 0.14%。99.9% 的算力在等待数据。

所以 Decode 阶段的理论速度上限是 约 24 token/秒， 与模型大小成反比。这也解释了为什么 7B 模型比 70B 快十倍—— 不是因为它算得少，而是因为它读得少。

推论：批量处理是 Decode 阶段最重要的优化。 一次读权重，同时给 32 个用户算，吞吐量能提升几十倍。 这就是下面要讲的连续批处理。

14.2 KV Cache：一个必须理解的优化

先看没有 KV Cache 会怎样。生成第 100 个 token 时，输入是前 99 个 token。 模型要做自注意力，需要计算这 99 个位置的 Q、K、V。

但注意：前 98 个位置的 K 和 V，在生成第 99 个 token 时已经算过了， 它们完全没有变化。每次重新算一遍是纯粹的浪费。

KV Cache 的原理。把已经算过的 Key 和 Value 缓存起来， 每步只计算新 token 的 KV，然后拼接。生成速度能提升几十倍。
⚠KV Cache 的代价：显存

天下没有免费的午餐。KV Cache 省了计算，但吃了显存。 而且它的增长速度非常快——正比于层数 × 上下文长度 × 并发数。

一个 70B 模型的 KV Cache 在 32K 上下文、单条对话下就能占到 5 GB； 如果同时服务 32 个用户，就是 160 GB——比模型权重还大。

这就是为什么长上下文服务很贵，也是 GQA、MQA、KV 量化等技术出现的原因。 下面这个计算器可以帮你估算：

（估算假设使用 GQA，KV 头数是注意力头数的一半。）

14.3 量化：把模型塞进小显卡

量化的核心思想是：用更少的位来表示每个权重。 神经网络对精度的要求远没有我们想象的那么高—— 把 fp16 压到 int4，模型大小变成 1/4，而效果通常只掉几个百分点。

精度7B 模型大小质量损失说明
fp3228 GB基准训练用，推理太浪费
bf16 / fp1614 GB几乎无损推理的默认选择
int87 GB几乎无损非常安全的选择
int43.5 GB轻微下降消费级显卡的最佳平衡点
3-bit / 2-bit2.6 / 1.8 GB明显下降需要特殊方法（如 GPTQ + 校准）

量化的基本原理

最朴素的量化是线性量化：把浮点数映射到整数区间。

$$q = \text{round}\!\left(\frac{w - w_{\min}}{w_{\max} - w_{\min}} \times (2^b - 1)\right)$$ $$\hat{w} = w_{\min} + q \times \frac{w_{\max} - w_{\min}}{2^b - 1}$$
$b$ 是位宽。量化时存储 $q$ 和缩放系数，推理时反量化回浮点

关键问题是：应该按什么粒度确定 $w_{\max}$ 和 $w_{\min}$？ 如果整个矩阵共用一个范围，那些数值很小的权重会被压成 0； 如果每个权重单独一个范围，那就要额外存储缩放系数，失去意义。

常见的粒度选择：

  • 逐张量：整个权重矩阵一组参数。最省，但精度损失大。
  • 逐通道：每个输出通道一组。常用方案。
  • 分组（group-wise）：每 64 或 128 个权重一组。GPTQ/AWQ 的做法， 精度损失最小，是现在的主流。
✓几种主流量化方案的取舍

GPTQ：训练后量化（PTQ）。用一批校准数据， 逐个权重地量化，每量化一个就调整剩下的权重来补偿误差。 4-bit 下质量很好，是目前最常用的方案之一。

AWQ：观察到「只有 1% 的权重是重要的」， 于是按重要性加权，保护那些关键通道。质量通常略优于 GPTQ，速度也更快。

GGUF（llama.cpp）：支持 CPU 推理，在 Mac 上表现极好。 适合本地部署和个人使用。

QLoRA：把量化用在训练上——把基座模型量化成 4-bit 冻结， 只训练 LoRA 适配器。这让你能在一张 24GB 显卡上微调 33B 模型。第 15 章会讲。

⚠量化的一个容易忽略的坑

量化的主要代价不是「效果变差」，而是对异常值极其敏感。 某些权重通道的数值可能比平均值大 100 倍（叫「异常通道」）， 它们会把量化的动态范围撑开，导致其他权重全被压成同一个值。

这就是为什么「per-tensor」量化的效果远不如「group-wise」。 也是为什么现代大模型在架构上要加 QK-Norm—— 从源头上抑制激活值的异常。

14.4 采样策略：怎么让输出不无聊也不胡说

模型输出的是词表上的概率分布。怎么从这个分布里挑一个 token，是一个独立的工程问题。

最朴素的做法是贪心搜索（每次选概率最高的），但它有两个问题： 输出会非常单调、容易陷入重复循环（「我觉得我觉得我觉得……」）。

所以实践中都用随机采样，但要对分布做调整。亲手试一下：

◈top-k 和 top-p 的区别

top-k 是固定的候选数量。不管分布长什么样，都保留 50 个。 问题是：如果分布很尖（模型很确定），50 个里大部分是垃圾； 如果分布很平（模型很犹豫），50 个可能还不够。

top-p 是固定的概率质量。保留累计概率到 0.9 的那些候选。 模型确定时可能只保留 2 个，犹豫时保留 200 个。 这是自适应的，所以通常效果更好。

实践中常见的组合是「temperature + top-p」，或者「temperature + top-k」， 很少三个一起用——调参空间太大反而难调。

14.5 批处理：吞吐量的关键

回到第 14.1 节那个洞察：Decode 阶段的瓶颈是显存带宽， 而且读一次权重只生成一个 token 太浪费了。

如果同时给 32 个用户生成呢？权重还是读一次，但算了 32 个 token。 吞吐量提升 32 倍，而总延迟几乎不变。

连续批处理。不再等整批一起结束，而是每步都动态调整批次成员。 这一项优化通常能把吞吐量提升 5~20 倍，是 vLLM 等框架最核心的能力。

PagedAttention：把操作系统思想搬进显存

连续批处理带来了一个新问题：KV Cache 的内存怎么管理？ 如果为每个请求预分配最大长度的空间，会浪费 60%~80% 的显存 （因为大部分请求用不到那么长）。

vLLM 的 PagedAttention 借鉴了操作系统的虚拟内存分页： 把 KV Cache 切成固定大小的「页」（比如 16 个 token 一页）， 按需分配，用一张表记录逻辑位置到物理页的映射。

效果：显存浪费从 60%~80% 降到 4% 以下，同样的硬件能同时服务 2~4 倍的请求。 这是一个纯粹的工程创新，没有任何算法上的改动，却带来了数倍的提升。

14.6 部署选型

场景推荐方案理由
个人本地试用 Ollama / llama.cpp + GGUF 量化 一行命令跑起来，支持 CPU 和 Mac 统一内存，4-bit 的 7B 只要 4GB
单机多并发服务 vLLM / SGLang 连续批处理 + PagedAttention，吞吐量比朴素实现高一个数量级
生产环境大规模 vLLM + TensorRT-LLM + 多机部署 极致性能，支持张量并行、投机解码、前缀缓存
边缘设备 llama.cpp / MLC-LLM 支持手机、树莓派，CPU/GPU 混合推理
不想运维 云 API 按 token 付费，没有硬件和运维成本，但有数据隐私和成本上限问题

两个必须分开看的指标

TTFT（首 token 延迟）

从发出请求到收到第一个 token 的时间。由 Prefill 阶段决定。 对交互式应用最重要——用户能忍受慢，但不能忍受「没反应」。

TPOT（每 token 延迟）

生成每个后续 token 的平均时间。由 Decode 阶段决定。 决定了「读起来流不流畅」。通常要求小于 50ms，否则会感觉卡顿。

吞吐量（tokens/s）

整个系统每秒能生成多少 token。由批处理效率决定。 这是成本指标——吞吐越高，每个 token 越便宜。

三者的矛盾

增大批量能提高吞吐，但会拉高每个请求的延迟。 优化目标取决于业务：聊天机器人要低延迟，离线批处理要高峰值吞吐。

为什么 Decode 阶段是显存带宽瓶颈，而不是算力瓶颈？

因为生成一个 token 时，计算量极小但需要读取的数据极大。

具体来说：生成 1 个 token，要把全部模型权重从显存读一遍。 70B 的 bf16 模型是 140 GB，H100 的显存带宽是 3.35 TB/s， 所以读一遍要 42 毫秒。

而这一遍读取对应的计算量只有约 $2\times70\text{B} = 1.4\times10^{11}$ FLOPs， 而 H100 的 bf16 峰值是 $989\times10^{12}$ FLOPS， 理论上 0.14 毫秒就能算完。实际耗时是理论值的 300 倍， 全部消耗在等待数据搬运上。

这个分析直接推出两个结论：① 模型越大，生成越慢，且成正比； ② 批处理能极大提升吞吐，因为读一次权重可以同时算多个请求。

KV Cache 省了计算，但代价是什么？怎么缓解？

代价是显存，而且增长很快： KV Cache 大小 = 2 × 层数 × KV 头数 × 头维度 × 序列长度 × 并发数 × 字节数。

缓解手段有四个方向：

① GQA / MQA：让多个 Query 头共享一组 KV 头， 直接把 KV Cache 缩小 4~8 倍。现代大模型的标配。

② KV 量化：把 KV Cache 也量化成 int8/int4，再省一半到四分之三。

③ PagedAttention：用分页机制按需分配，把浪费从 60~80% 降到 4%。

④ 减少并发或上下文长度：最直接但会影响服务能力。

temperature 和 top-p 有什么区别？该调哪个？

temperature 改变的是整个分布的形状—— 它把所有 logits 除以 T，让分布整体变尖或变平。所有候选词都会受影响。

top-p 改变的是候选集的大小—— 它按概率从高到低累加，到 p 为止，把剩下的直接砍掉。 分布形状不变，只是尾巴被切了。

该调哪个：temperature 是主力，它直接控制「创造性」； top-p 是安全网，用来砍掉长尾里的荒谬选项。

推荐做法：先固定 top-p = 0.9，然后只调 temperature。 代码和数学任务用 0.1~0.3，日常对话 0.7，创意写作 1.0~1.2。 如果输出出现重复循环，加一点 repetition penalty（1.05~1.15）。

为什么连续批处理能提升 5~20 倍吞吐量？

因为静态批处理有一个巨大的浪费：整批必须等最长的那个请求完成。

假设一批里有 3 个请求，分别需要生成 10、100、50 个 token。 静态批处理下，前 10 步三个都在跑，但从第 11 步开始， 请求 A 已经完成了，它的槽位只能空着，一直到第 100 步请求 B 结束。 平均 GPU 利用率可能只有 50% 左右。

连续批处理的做法是：每生成一个 token 就检查一次， 有请求完成就立刻把等待队列里的新请求放进来。 这样槽位几乎永远是满的。

结合 Decode 阶段「读一次权重能算多个请求」的特性， 填满槽位就等于把显存带宽利用到极致。实测吞吐提升通常在 5~20 倍之间。

为什么 int4 量化后效果只掉一点点，而 int2 就崩了？

因为神经网络权重分布有一个特点：大部分权重都很小，只有少数很重要。

int4 有 16 个量化级别，配合 group-wise 缩放， 足以区分「很重要」「一般」「接近 0」这几个档次。信息损失可以接受。

int2 只有 4 个级别，意味着权重只能被归到 4 个值上。 这时候「0.01」和「0.03」会被压成同一个值， 而它们在网络里可能承担完全不同的功能。信息损失是灾难性的。

另外，int2 需要非常精细的校准和混合精度策略（比如保留一部分层为 int8）， 才能勉强可用。这也是为什么「2-bit 量化」虽然有论文， 但在实际部署中很少见到。

但很多时候你需要的是一个自己的模型： 懂你的业务术语、会用你的数据格式、符合你的语气风格。
