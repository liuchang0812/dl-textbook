第 17 章 · 第六部 应用篇

检索增强生成 RAG

模型不知道你的私有数据，也不知道昨天发生了什么。 RAG 的解法是让它开卷考试：先从你的资料库里检索相关内容， 再把它们塞进提示词，让模型基于这些材料回答。 这一章讲清楚整条流水线，以及为什么 90% 的 RAG 问题都出在检索，而不是生成。

⏱ 约 28 分钟 🎯 能独立设计并调优一个 RAG 系统 🧪 1 个交互演示

17.1 为什么要 RAG

大模型有三个无法通过提示工程解决的限制：

① 不知道私有数据

模型只见过公开数据。你公司的制度、产品文档、客户记录，它一概不知。

② 知识有截止日期

训练数据截止到某个时间点。之后发生的事情，模型完全不知道。 而且重训一次的成本是千万美元级别。

③ 无法给出出处

即使它「碰巧」答对了，你也无法验证。在严肃场景下， 没有出处的答案等于没有答案。

④ 会自信地编造

不知道答案时，模型不会说「不知道」，而是生成一个听起来很合理的答案。 这是第 19 章要讲的幻觉问题。

RAG（Retrieval-Augmented Generation，检索增强生成）一次性解决这四个问题。 它的核心思想朴素得让人意外：

RAG 的本质

与其让模型「记住」知识，不如在回答时把相关资料递给它。

这就像考试：闭卷考试要求你把所有知识背下来， 而开卷考试只要求你会查资料。 人类的专业知识工作几乎都是开卷的——律师、医生、工程师， 没有人靠记忆力工作，他们靠的是检索和判断。

RAG 让模型也这样做。而且知识更新变得极其简单： 改向量库就行，不用重新训练模型。

17.2 完整流水线

RAG 的完整流水线。上半部分是离线索引（做一次）， 下半部分是在线查询（每次请求都跑）。中间用向量库连接。

17.3 分块：最容易被忽视的关键环节

文档不能整篇塞进向量库——一份 100 页的 PDF 变成一个向量， 会让所有细节都被平均掉，检索出来也没用。所以要切成小块。

但切法非常讲究：

策略做法优点缺点
固定长度 每 512 个 token 切一块 简单，块大小一致 可能从句子中间切断，语义不完整
按结构切 按标题、段落、列表项切 保留语义完整性 ✅ 块大小差异大
递归切分 先按大结构切，超长再按小结构切 兼顾语义与大小 ✅ 实现稍复杂
语义切分 用嵌入模型检测语义边界 边界最自然 慢，且提升不稳定
父子块 检索用小块的向量，返回时给父块 检索准 + 上下文全 ✅✅ 需要额外存储结构
✓分块的五个实用建议

1. 块大小 200~800 token 是常见的甜点区。 太小会丢失上下文（「它增长了 15%」——什么增长了？）， 太大则检索精度下降（一个块里混了太多主题，向量被平均）。

2. 一定要有重叠（overlap）。 相邻块之间重叠 10%~20%，防止关键信息正好落在切分点上被割裂。

3. 给每个块加上下文头。 在块的开头补上「文档标题 + 章节名」， 这样即使块本身很短，向量也能携带全局信息。 这是最简单有效的改进之一。

4. 保留元数据。文档来源、更新时间、权限标签。 检索时可以按元数据过滤，也方便在答案里标注出处。

5. 表格和代码要特殊处理。 直接按字符切会把表格切得面目全非。 表格应该整体作为一个块，或者转换成 Markdown 保留结构。

17.4 向量检索：把语义变成距离

嵌入模型把文本映射成一个高维向量，语义相近的文本向量也相近。 检索就是找出与查询向量最接近的几个文档块。

$$\text{similarity}(\mathbf{q}, \mathbf{d}) = \frac{\mathbf{q} \cdot \mathbf{d}}{|\mathbf{q}||\mathbf{d}|}$$
余弦相似度，只看向量方向，不看长度。范围 -1 到 1，越接近 1 越相似

Top-K（检索几条）3

检索结果排名

橙色点是查询，蓝点是被检索到的文档块。虚线表示「被选中」。 试着把 K 调到 5——你会发现排名 3、4、5 的「病假 / 产假 / 加班」虽然 在向量空间里离「年假」很近，但它们并不回答这个问题。 这就是为什么需要重排序。

⚠纯向量检索的三个盲区

1. 精确匹配很差。查询「错误码 E4021」， 向量检索可能返回一堆「其他错误码」的文档，因为它们在语义上相似。 但它找不到那个精确包含 E4021 的文档。

2. 对否定和数字不敏感。 「不含防腐剂的食品」和「含防腐剂的食品」在向量空间里非常接近。

3. 语义相近 ≠ 能回答问题。 就像上面的演示：所有请假制度文档都语义相近， 但只有关于年假的那几条能回答问题。

这三个盲区正是「混合检索」和「重排序」存在的原因。

17.5 混合检索：向量 + 关键词

既然向量检索不擅长精确匹配，那就把它和传统的关键词检索结合起来。 这就是混合检索（Hybrid Search）。

方法原理擅长不擅长
BM25（稀疏） 基于词频和逆文档频率 精确关键词、专有名词、错误码 同义词、语义改写
向量检索（稠密） 语义嵌入 + 余弦相似度 语义相似、跨语言、模糊描述 精确匹配、罕见词
混合检索 两路并行，融合排序 两者兼得 ✅ 需要调融合权重

融合方法：RRF

两路检索的分数尺度不同，不能直接相加。常用倒数排序融合（RRF）：

$$\text{RRF}(d) = \sum_{r \in \text{检索器}} \frac{1}{k + \text{rank}_r(d)}$$
$k$ 通常取 60。只看排名，不看分数，避免了尺度不一致的问题

RRF 的巧妙之处在于只用排名，不用分数。 这样就不需要归一化两个完全不同的分数分布， 而且对分数异常值天然鲁棒。

重排序：最后一道关卡

检索阶段追求快（要扫过几百万个向量）， 所以用的是「双塔」结构：查询和文档分别编码，然后算相似度。 这种方式无法建模查询和文档之间的细粒度交互。

重排序（Rerank）阶段只处理检索出来的 Top-50， 可以用更强的交叉编码器（cross-encoder）： 把查询和文档拼在一起送进模型，输出一个相关性分数。

两阶段检索。先用双塔从百万文档里粗筛出 50 条（快）， 再用交叉编码器精排取前 5 条（准）。这是工业界 RAG 的标准架构。

17.6 生成阶段：怎么用好检索到的材料

检索做好了，生成阶段其实很简单。但有几个细节很关键：

✓生成阶段的五个关键设计

1. 强制引用编号。这不仅能让你验证答案， 还会显著降低幻觉——因为模型知道每个陈述都要有出处， 它会倾向于只使用资料里的内容。

2. 明确允许「不知道」。 「如果资料不足，说『无法回答』」这一条极其重要。 没有它，模型会硬答。

3. 要求处理矛盾。检索到的资料经常互相冲突 （旧版本和新版本的制度并存）。让模型指出矛盾比让它选一个更安全。

4. 在资料里带上来源信息。 不只是正文，还有文档名、章节、更新时间。 模型可以据此判断哪个更新、更权威。

5. 控制资料数量。不要把所有检索结果都塞进去。 5~10 条通常足够，多了反而因为「lost in the middle」而降低质量。

17.7 常见失败模式与诊断

症状根因怎么修
答案里有资料里没有的信息 模型在用自己的知识补充 强化提示词的约束；强制引用；降低 temperature
检索不到正确的文档 分块切断了关键信息；嵌入模型不适配领域 调整分块大小和重叠；加混合检索；换领域适配的嵌入模型
检索到了但不被使用 资料放在上下文中部被忽略；资料太长被截断 把最相关的放首尾；减少资料数量；加大 max_tokens
答案不完整 Top-K 太小，漏掉了相关块 增大检索数量 + 用重排序筛选；考虑「多跳检索」
把旧信息当新信息 没有时间维度的排序 元数据里带时间戳，检索时优先返回新版本
答非所问 查询本身模糊，或检索时用了原始查询 做「查询改写」：先让模型把问题重写成更适合检索的形式

查询改写：一个高性价比的优化

用户的提问方式和文档的表述方式往往不同。用户问「年假怎么请」， 文档写的是「年度带薪休假申请流程」。直接检索效果不好。

几种改写策略：

  • HyDE：先让模型「假装回答」这个问题， 再用生成的假答案去检索。因为假答案的表述风格更接近真实文档。
  • 多查询：让模型生成 3~5 个不同角度的查询，分别检索后合并结果。
  • 问题分解：「年假怎么请、能攒吗」拆成两个独立查询分别检索。
  • 指代消解：多轮对话中，「它呢？」需要结合历史补全成完整查询。

17.8 怎么评估 RAG

RAG 有两个环节，必须分开评估，否则你无法定位问题。

检索质量

Recall@K：正确的文档块有没有出现在 Top-K 里？
MRR：正确块的排名平均有多靠前？
Precision@K：Top-K 里有多少是真正相关的？

生成质量

忠实度（Faithfulness）：答案是否完全基于检索到的资料？
相关性：答案是否回答了问题？
引用准确性：标注的来源是否正确对应？

先修检索，再修生成。 如果 Recall@5 只有 60%，说明 40% 的问题根本没找到正确的资料， 这时候无论怎么优化提示词都没用。

✓搭建 RAG 评测集的最快方法

不需要人工标注几百条。一个实用的做法是：

① 从你的文档里随机抽 50 个块， 让一个强模型为每个块生成 2~3 个「这个块能回答的问题」。
② 用这些问题跑检索，看对应的块能不能被召回。 这就是 Recall 指标。
③ 再跑完整 RAG，用另一个模型判断答案是否忠实于检索到的资料。

这套流程半天就能搭起来，能覆盖 80% 的常见问题。 比「凭感觉调提示词」高效得多。

为什么说「90% 的 RAG 问题出在检索」？

因为生成阶段的上限完全由检索质量决定。

如果正确的资料没有被检索出来，无论提示词写得多好、模型多强， 它都不可能给出正确答案——巧妇难为无米之炊。 反过来，如果检索出了正确的资料，即使是一个中等水平的模型， 配合一个好的提示词也能给出不错的答案。

实践中的表现就是：很多人遇到 RAG 效果差， 第一反应是改提示词、换更大的模型，结果提升有限。 正确的做法是先测 Recall@K—— 如果它低于 80%，说明问题在检索，应该去调分块策略、加混合检索、换嵌入模型。

为什么需要重排序？只用向量检索不行吗？

因为检索和排序的目标不同：检索要快，排序要准。

向量检索用的是「双塔」结构：查询和文档分别编码成向量，然后算相似度。 这样文档向量可以预先算好并建立索引，检索百万文档只要几十毫秒。 但代价是——查询和文档之间没有任何交互， 只是两个独立向量的点积，无法捕捉细粒度的语义关系。

交叉编码器把查询和文档拼在一起送入模型， 每个词都能和对方的每个词交互，准确率显著更高。 但它必须对每一对查询-文档都跑一次，百万文档要跑百万次，完全不可行。

所以两阶段架构是必然的：双塔从百万里粗筛出 50 条（快）， 交叉编码器从 50 条里精排出 5 条（准）。 这就是「召回 + 精排」的经典模式。

分块时为什么要在块的开头加上文档标题和章节名？

因为孤立的块会丢失上下文。

假设一个块的内容是「申请需提前 3 天在系统提交」。 单独看，这个块说的是什么？请假？报销？采购？ 嵌入模型无法判断，它生成的向量会很模糊， 检索时可能匹配到任何「提前提交」相关的查询。

如果改成「员工手册 2025 版 · 4.2 节 年假申请：申请需提前 3 天在系统提交」， 向量的语义就明确了——它明确属于「年假」这个主题。

这个技巧叫「上下文头」（contextual header）， 是成本最低、收益最明显的 RAG 优化之一。 它不需要换模型、不需要重新索引，只是改一下文本预处理。

RAG 和微调该怎么选？能一起用吗？

判断标准：知识 vs 行为。 需要改变模型「知道什么」用 RAG， 需要改变模型「怎么做」用微调。

能一起用，而且效果往往最好。典型的分工是：

· RAG 负责提供准确、可更新、可引用的事实知识。
· 微调 负责让模型学会你期望的输出风格、格式、术语和推理方式。

举例：一个医疗问答系统，用 RAG 提供最新的临床指南， 用微调让模型学会用医生的口吻、按「诊断-依据-建议」的格式输出， 并且知道什么情况下必须建议就医。

顺序建议：先做 RAG，再做微调。 因为 RAG 的迭代周期是天级的，微调是周级的。 先用 RAG 把效果拉到可用，再考虑微调做精细化。

如果模型回答里出现了资料中没有的信息，你会怎么排查？

按这个顺序排查：

① 先看检索结果。把实际送进提示词的资料打印出来。 很可能正确的资料根本没被检索到，模型只能用自己的知识硬答。 这是最常见的原因。

② 看提示词约束。有没有明确说「只使用资料中的信息」？ 有没有要求「资料不足时说明无法回答」？ 缺少这两条约束时，模型会很自然地用自己的知识补充。

③ 看 temperature。温度太高会增加模型自由发挥的概率。 知识问答场景建议 0~0.3。

④ 看引用标注。如果要求强制标注 [1][2]， 但没有出处的陈述还是出现了，说明提示词的约束力度不够， 可以考虑用结构化输出（要求每条陈述都必须带 citation 字段）。

⑤ 加自动检查。用一个独立的模型（或规则） 检查答案里的每个事实性陈述是否能在资料中找到依据， 不通过的重新生成或标注警告。
